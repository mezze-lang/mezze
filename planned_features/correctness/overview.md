# Correctness Tooling for Mezze

## The Shift

Code is increasingly generated by LLMs. The developer's job shifts from writing code to verifying intent. The question is no longer "how do I implement this?" but "did the generated code do what I meant?"

Types catch structural errors. But logic errors — wrong comparisons, missing edge cases, off-by-one boundaries, incorrect branches — pass the typechecker. Writing tests works but is high-friction for spot-checking generated code.

## Philosophy

**Make correctness visible, not provable.** Show developers concrete behavior and let them spot wrongness. Humans are good at recognizing wrong outputs, bad at imagining all inputs. The tools generate the inputs; the developer reads the outputs.

## Why Mezze Is Uniquely Suited

- **Named fields** — generated examples are self-documenting without context
- **Full type inference** — tools know exact input shapes without developer annotation
- **Effect annotations** — types distinguish pure functions (trivially runnable) from effectful ones (need handlers)
- **Swappable handlers** — effectful functions made runnable by user-provided handlers
- **Closed variants** — tools enumerate every constructor, no hidden cases
- **Row polymorphism** — open records tell tools which fields are required vs optional
- **Immutability by default** — reproducible runs, trivial trace recording, safe replay

## Tools

### `mez sample` — [sample.md](sample.md)

Auto-generate inputs from a function's type signature, execute, show input-output pairs. The core tool.

- **Default mode** — type-driven edge cases (~8 smart inputs)
- **Cover mode** (`--cover`) — generate inputs that hit every branch and match arm
- **Boundary mode** (`--boundaries`) — test both sides of every comparison
- **Pipeline view** — show intermediate values at each step of dot/pipe chains
- **Interactive** — [m]ore cases, [f]ocus on one argument, [c]ustom input, [s]hrink a failing case
- **Effects** — user provides handlers explicitly: `mez sample perform Handler in module::func`
- **LSP** — CodeLens, inline pipeline values, sample panel

### Debugging — [debugging.md](debugging.md)

Explore execution in depth when sample reveals something suspicious.

- **Trace** — recorded execution, browse any step freely, step into function calls
- **Pipeline-aware debugging** — step over or step through dot/pipe chains with intermediate values
- **Live edit** — replace any expression with a type-compatible alternative, replay from that point, rerun all samples
- **Provenance** — trace a value backward through transformations to its origin in the input
- **Contract inference** — discover properties from many samples, save as regression checks

### Continuation Capture — [continuation-capture.md](continuation-capture.md)

Live replayable coredumps. When a crash happens (in sample, tests, or production), capture the full computation state as a portable `.cont` file. Replay it later with full debugging — step through, inspect values, live edit code, share with teammates. Like a coredump but small, readable, replayable, and editable.

- **Auto-capture** — sample captures continuations on crash automatically
- **Replay** — `mez replay file.cont` opens the debugger with all runtime values
- **Live edit** — change code in the replay, see different results
- **Shareable** — the `.cont` file IS the bug report, works on any machine
- **CaptureOnCrash handler** — effect handler for production use

### AST-Aware Property Testing — [property-testing.md](property-testing.md)

The library counterpart to `mez sample`. Developer writes boolean properties, the library generates smart inputs and checks them automatically. Unique because the library is AST-aware — it uses Mezze's comptime + reflection macros to analyze the function under test at compile time, extracting branch conditions, comparison constants, and argument relationships to generate boundary-targeted inputs. No special compiler support beyond the reflection API — entirely userland.

- **`type_gen`** — type-driven generation (like QuickCheck)
- **`ast_gen {func}`** — AST-aware generation via comptime + reflection
- **Automatic shrinking** — minimize failing inputs
- **Coverage reporting** — track which branches were exercised
- **Effectful functions** — user provides handlers via `perform` field

### Truffle Instrumentation — [instrumentation.md](instrumentation.md)

GraalVM Truffle provides DAP debugging (breakpoints, stepping, variable inspection), profiling, and coverage — but Mezze hasn't wired it up yet. The foundation exists (SourceInfo on every IR node, frame descriptor with named slots) but the instrumentation layer is missing. The doc covers what's needed and the implementation phases.

### Refactoring — [refactoring.md](refactoring.md)

Mezze's content-hash architecture makes refactoring safe — definitions are identified by hash, not name. Rename, extract function, inline, move, dead code detection, and change signature are all structurally straightforward because hash-based references don't break when names or locations change.

## Workflow

1. LLM generates a function
2. Developer clicks "Sample" in editor (or runs `mez sample` in CLI)
3. Glances at 8 input-output pairs — most bugs caught here
4. If suspicious: use `--cover` to see all branches, `--boundaries` to check edge values
5. If still unclear: trace into a specific case, browse execution, try live edits
6. If satisfied: move on. Total overhead: one click, a few seconds of reading.

## Future Directions

Ideas inspired by Clojure's REBL/Reveal/Portal ecosystem and Elm's time-travel debugger. These require richer UI surfaces (web-based tool or editor webviews) beyond the CLI + LSP inlay hints that the core tools target.

### Browse — Interactive Value Navigation

When sample returns complex nested data, let the developer drill into it interactively. Click a record field to see its value. Click a map entry to see its contents. Navigate back up. Every value is explorable, not dead text.

Inspired by Clojure's datafy/nav protocol — any value can be turned into browsable data, and selecting something produces the next thing to look at. Works as text-based numbered navigation in CLI (`> 1`, `> ..`), but the full experience needs a graphical UI: tree views, table views for sequences of records, expandable nested structures.

### Rich Crash Messages

When sample reveals a crash, show Elm-style explanations instead of stack traces. Since we're executing with known inputs, the message can include the concrete values that caused the crash:

```
I ran into a problem at line 3:

    let avg = items.fold {init = 0, f = ...} / items.length {}
                                                ^^^^^^^^^^^^^^^
items.length {} returned 0, and dividing by 0 is not allowed.

Hint: Consider checking if items is empty before dividing.
```

This works in CLI and LSP — no special UI needed. The key insight: because sample knows the exact inputs, error messages can be concrete rather than abstract.

### Watch — Scrub Through Cases in the Editor

In the LSP, a mode where the developer selects a sample case from a dropdown and all inline annotations update to show values for that case. Arrow keys flip between cases. The developer sees how the same code behaves on different inputs without leaving the editor.

```
Case: [1/8] {items = [3, -1, 0, 5]}          [< >]

items                                          # [3, -1, 0, 5]
  .filter {p = {x} -> x > 0}                  # [3, 5]
  .map {f = {x} -> x * 2}                     # [6, 10]
```

Switch to case 2, everything updates:

```
Case: [2/8] {items = []}                      [< >]

items                                          # []
  .filter {p = {x} -> x > 0}                  # []
  .map {f = {x} -> x * 2}                     # []
```

Inspired by Elm's time-travel debugger scrubbing — but instead of scrubbing through time/messages, scrubbing through different inputs to the same function.

### Diff — Behavioral Regression Check

Compare a function's behavior before and after a code change. Run the same auto-generated inputs through the old version (from git) and the new version, show where outputs differ:

```
$ mez diff module::process

  Behavioral diff (8 samples):
    {x = 0}   -> 0    (unchanged)
    {x = 5}   -> 10   (was 5)     CHANGED
    {x = -1}  -> -1   (unchanged)
```

No expected values needed — just "did the behavior change, and where?"

### Visual Data Rendering (`mez ui`)

A web-based UI for exploring sample results, traces, and complex data structures graphically. Tables for sequences of records, tree views for nested data, charts for numeric patterns. The full REBL/Portal experience but for Mezze. Separate from the core CLI + LSP tools.
