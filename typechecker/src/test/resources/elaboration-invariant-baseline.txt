# WHAT ACTUALLY HOLDS THEM OPEN, measured. A constructor node is stamped from
# `callReturnTypes[loc]` (per-loc) in preference to the pushed context type. For
# these nodes the two are both solved, both substituted, and they name DIFFERENT
# type variables for the same type:
#
#   None at option.mz:139   per-loc = Option 'a(27584)   context = Option 'f583(27592)
#
# and the declaration's own scheme quantifies the second. So the node carries a
# variable the scheme does not bind, and the gate — which compares by NAME, over-
# approximating on purpose — reports it. This is the recurring "one written type
# variable becomes two" defect, not a fold and not a receiver.
#
# It is ORDER-DEPENDENT, which is the cleanest evidence that it is a solver
# artifact rather than a property of the code: swapping the two arms of
# Option.flatten so the bare constructor comes FIRST makes the row disappear.
#
# NARROWED FURTHER (2026-09-20), and this is the statement to act on. Traced the
# whole chain for the repro and everything on the way is CORRECT:
#   - `generateVariantConstruction` gives `None` a fresh var + a HasConstructor,
#     and `VariantSolver` instantiates the declaration's params with fresh vars —
#     so the node's variable is not the type declaration's leaking out.
#   - `TypeAnnotationConverter` threads ONE `typeVarCache` through a whole
#     annotation, so a single written `'a` is one variable across params and
#     return. The "annotation converted twice" shape is NOT what this is.
#   - `generateMatch` emits `Equality(arm, resultVar)` for EVERY arm, and the
#     solve honours it: for `Option.flatten` the arms and `resultVar` all end up
#     in one class (`'c#245 -> Option 'a`).
#
# What is NOT in that class is the DECLARED RETURN. At emit the pushed context
# (the declaration's own return type, substituted) reads `Option 'f583` while the
# match result reads `Option 'a`. Both are substituted, and neither resolves to
# the other: two live roots. Whichever of the two a node happens to be stamped
# from decides whether the gate sees it as bound, and that is what the arm order
# changes.
#
# WHY they are two roots is NOT yet established, and one plausible answer has
# already been checked and is WRONG: `bindLet` DOES emit
# `Equality(exprResult.type, annotatedType)`, so it is not that the annotation is
# merely validated against the body instead of unified with it. The remaining
# candidate is that the two are solved in DIFFERENT solves (the per-binding solve
# and the module solve) so the equality never relates these two instances — the
# same split the `enumerate` fix had to cross. That is a hypothesis, not a
# measurement; whoever picks this up should confirm it before acting.
#
# What IS settled: the fix is not "pick the right one at emit" (measured twice,
# below) and not in the match — the arms and the result var are correctly one
# class already.
